10  Working with AI assistants

How can an AI assistant help me with R code, and what do I need to check myself?

When you get stuck while programming, you probably ask an AI assistant first: a program that answers questions asked in everyday language with text and code. For R, this is often helpful. An assistant finds typos, explains error messages and suggests code for steps you do not know yet. But it knows neither your data nor every package, and it does not tell you on its own when it does not know something. This chapter covers how to give an assistant enough context, how to check its answers and which data you must not give it.

Note

Research journal: Where are you in your mini study? Your analysis is in place: scales, group comparisons, factor analysis and regression models. If you extend it, for example with another variable or a different model, an assistant can help you with the code. The ALLBUS data stay on your computer. Section 10.6 explains why.

10.1 What this chapter is about

An AI assistant is based on a language model, a program that has learned from a very large amount of text how a text is likely to continue. If you ask for R code, it writes code that resembles the code in its training texts. This works well for common tasks, because it has seen many examples of them. It has seen few or no examples of rare packages such as mariposa. In that case the code often looks correct even though it is not.

Assistants come in different forms. Some run as a chat in the browser, some complete code directly in the development environment. Others work as an agent: they read files in your project folder on their own, run commands and change code. These programs change quickly. The way of working in this chapter is therefore not tied to any particular program and works with any assistant.

An assistant writes code faster than you. Whether the code does the right thing is for you to check, and for that you need the basics from the previous chapters: you have to be able to read what a pipeline does and to recognise whether a result is plausible. You remain responsible for every line of code and every number in your work.

What you will be able to do after this chapter

  • Explain why an AI assistant may invent functions and arguments for mariposa.
  • Write a request that gives context: goal, package versions, documentation, variables and error message.
  • Check suggested code with the R help and your own plausibility checks.
  • Reproduce a problem with made-up example data instead of passing on real data.
  • Decide what you may show an assistant under the GESIS terms of use.
  • Declare the use of an assistant in coursework or a thesis.

10.2 What an assistant knows about R

A language model learns from texts that were collected up to a certain cut-off date. It does not know what appeared after that date, unless the program also searches the web. It knows little about what rarely occurs in those texts. For R, this means:

  • It knows base R, dplyr and ggplot2 well, because the web has a great deal of code and many answered questions about them.
  • Older ways of writing code are more common than new ones. You therefore often get %>% instead of |> (Section 3.7) or case_match() instead of recode_values() (Chapter 5).
  • Many answers follow the logic of SPSS or of other packages that solve similar tasks.
  • mariposa is young and used by comparatively few people. An assistant therefore often does not know its function names, or knows only those of an older version.

What it does not know, it fills in with whatever sounds plausible. If you ask for a weighted mean with mariposa, the answer may look like this:

allbus |>
  mariposa::weighted_mean(ls01, weights = wghtpew)
Error:
! 'weighted_mean' is not an exported object from 'namespace:mariposa'

A function with a similar name does exist, but as weighted.mean() in base R. In mariposa it is called w_mean(). With an invented name, R stops at once, before it even touches the dataset.

NoteBackground: Why assistants invent functions

A language model produces its answer piece by piece. At each step it chooses a continuation that is likely according to its training texts. It does not look up whether a function really exists, and it has no access to the packages on your computer. If the conversation so far has been about R and weighted means, weighted_mean is a very likely continuation. Whether mariposa has a function with this name plays no part in this choice. This is why invented functions sound just as convincing as real ones, and why it helps to give the assistant the real documentation.

You notice at once when an error stops the code. Harder to spot are suggestions that run without an error message and still calculate something other than what you want. Section 10.5 shows how to find such cases.

10.3 Giving context

10.3.1 What belongs in a request

An assistant sees only what you write to it. The more precisely it knows what you are working with, the less often it has to guess. This information is called context. For a question about R code, it includes:

  1. What you want to do, in one or two sentences and with the names of the variables.
  2. What you are working with: the versions of R and mariposa.
  3. The mariposa documentation. At https://yannickdiehl.github.io/mariposa/llms.txt there is an overview of all functions as a plain text file intended for language models. If your assistant can read web pages, the link is enough. Otherwise, copy the help page of the function in question into your request (for example ?w_mean).
  4. The variables with names, labels and values. This information is in the ALLBUS questionnaire and codebook, which are available on the GESIS study page.
  5. If there is an error, the code that causes it and the full text of the error message.

R prints the versions itself:

R.version.string
[1] "R version 4.6.2 (2026-10-29)"
packageVersion("mariposa")
[1] '0.7.4'
Importantmariposa tip: Names and labels as a table

Instead of typing out this information, you can print it as a table with codebook() (Chapter 4) and keep only the columns that describe the variables:

allbus |>
  codebook(mm01:mm06, eastwest, wghtpew, show_freq = FALSE, view = FALSE) |>
  as.data.frame() |>
  select(name, label, value_labels, missing_values)

For each variable, the table contains the name, the label, the value labels and the missing-value codes, which is the same information as in the GESIS codebook. Frequencies and case numbers are left out.

10.3.2 An example with made-up data

A problem often depends on the structure of the data, for example on missing values, labels or weights. A small reproducible example helps here: a few rows of made-up values that have the same structure as your data and show the same problem. The example runs without your data, and no answer from a real respondent leaves your computer.

example_data <- tibble(
  eastwest = c(1, 1, 1, 2, 2, 2),            # 1 = West, 2 = East
  ls01     = c(8, 7, NA, 6, 9, 5),           # life satisfaction, 0 to 10
  wghtpew  = c(1.2, 1.2, 1.2, 0.5, 0.5, 0.5) # weight
)
example_data
# A tibble: 6 × 3
  eastwest  ls01 wghtpew
     <dbl> <dbl>   <dbl>
1        1     8     1.2
2        1     7     1.2
3        1    NA     1.2
4        2     6     0.5
5        2     9     0.5
6        2     5     0.5

The values are invented. All that matters is that the example shows the problem: here a missing value in ls01 and a weight that differs between East and West. The reprex package copies such examples together with their output as text that you can paste into a request (see Further reading).

10.4 A template for your request

The following template brings the context together and lists the rules that apply in this book. Save it as a text file in your project and fill it in for each request. With these rules, the assistant writes code in the style of this book, and you can check that code with what you have learned in the chapters.

I am working in R (version: …) with the tidyverse and the mariposa package (version: …).
Documentation for mariposa: https://yannickdiehl.github.io/mariposa/llms.txt

Please follow these rules:
- Native pipe |> instead of %>%.
- Statistics and tests with mariposa functions, for example describe(),
  frequency(), t_test() or linear_regression().
- Weighting through the argument weights = wghtpew.
- Recoding with rec() inside mutate().
- The English-language ALLBUS file (ZA8833) does not declare missing values.
  I set them to NA with set_na() when I read the data with read_spss(),
  so they are already NA in my data.
- Use only functions and arguments that exist in the packages named above.
  If you are unsure about a function, say so.
- Explain each line in a short comment.

My variables (name, label, values):
…

What I want to do:
…

My code so far and the error message (if any):
…

The template contains no data, and what you fill in at the places marked … should not contain any either. Section 10.6 sets out what you may pass on.

Tip

SPSS → R: Translating old syntax. If you have SPSS syntax from earlier projects, an assistant can translate it into R. Syntax usually contains only commands and no data. Include the rules from the template in your request, because many mariposa functions correspond to an SPSS procedure: FREQUENCIES becomes frequency(), DESCRIPTIVES becomes describe(). Afterwards, check whether R prints the same numbers as SPSS did.

10.5 Checking answers

Read an answer before you run it. If you do not understand a line, ask until you do. Then check whether the suggested functions exist and whether the result is correct.

10.5.1 Does the function exist?

Look up every function you do not know with ? (Section 3.3). If RStudio finds no help page, the function probably does not exist in the loaded packages. help(package = "mariposa") lists all functions in the package. For a quick test, this is enough:

c("w_mean", "weighted_mean") %in% ls("package:mariposa")
[1]  TRUE FALSE

w_mean() exists, weighted_mean() does not. Check the arguments as well. Under Usage, the help page shows which arguments a function accepts. If an argument is misspelled, mariposa tells you:

example_data |>
  describe(ls01, weight = wghtpew)
Error in `describe()`:
! Unknown argument `weight` of `describe()`.
ℹ Did you mean `weights` instead of `weight`?

10.5.2 Does the code run, and is the result correct?

Run the code in a chunk of your Quarto document (Section 1.5.2). Then it is part of your report, and later you can trace where a number comes from.

Code that runs without an error message does not necessarily calculate the right thing. A common case is a mean without weights.

Question: What is the mean life satisfaction in the example, unweighted and weighted?

example_data |>
  summarise(mean = mean(ls01, na.rm = TRUE))
# A tibble: 1 × 1
   mean
  <dbl>
1     7
example_data |>
  w_mean(ls01, weights = wghtpew)

Weighted Mean Statistics
------------------------
Weights: wghtpew

  ---------------------------
  Variable   Mean  N  Missing
  ---------------------------
  ls01      7.179  4        1
  ---------------------------

Interpretation. Both calls run without a warning. The unweighted mean is 7.0, the weighted mean 7.179. In ALLBUS, the new federal states are deliberately over-represented (Chapter 7, section “Weighting”). An unweighted mean for Germany as a whole therefore gives the East too much weight. An assistant that does not know your data knows this only if you tell it.

Further checks take little time:

  • Number of cases: Does the N match what you expect? If many cases are missing, this is often due to missing values or a filter.
  • Range of values: The mean of a scale from 0 to 10 must lie between 0 and 10. Negative values point to missing-value codes that were counted as valid values (Section 4.8).
  • Weights: mariposa states in the header of the output whether the analysis is weighted, for example Weighted Mean Statistics.
  • Comparison with a known result: First reproduce a result you know from this book, such as a frequency from Chapter 4. If it matches, the pipeline works up to that point.

Always take the numbers for your report from your own R output. An assistant that has not seen your data cannot know any results. If it gives numbers anyway, they are made up.

10.6 Protecting data

What you write to an assistant is sent to the provider, processed there and often stored as well. Research data have their own rules for this.

Warning

Caution: ALLBUS data do not belong in an AI assistant. Section 4 of the GESIS terms of use (valid from 4 February 2026) prohibits using AI systems to process the data GESIS provides. GESIS may grant exceptions only on request in individual cases, and only if you alone have control over, and responsibility for, the AI system and use it exclusively for scientific purposes. Anyone who culpably breaches the terms loses the right of use and pays a contractual penalty of €10,000.

For working with this book, this means:

  • You can pass on code, error messages, variable names and labels from the public documentation, and examples with made-up values.
  • Keep the file ALLBUS2023.sav, data rows and any output that shows individual respondents (such as the output of head(), glimpse() or View()) to yourself.
  • The terms do not explicitly address aggregated results such as a frequency table. The safest approach is to ask for code and interpret the numbers yourself.
  • An agent that reads files in your project folder and runs R processes the data itself. Use such tools only in a folder without ALLBUS data.

Other datasets have their own terms of use. If you collect data yourself, for example in a survey for your thesis, you also have data protection obligations to your respondents. In both cases, check with your supervisor beforehand which tools you may use. Terms of use change; read the current version before you start a new project.

10.7 Assistants in coursework and theses

Your university decides whether and how you may use an assistant in assessed work. Many universities have their own guidance on this, often as part of the declaration of authorship. Read it before you start, and if in doubt, ask your supervisor.

If you use an assistant, state what you used it for, for example writing or correcting code or explaining error messages. To do this, keep a record of which requests you made and what you used from the answers. The simplest place for this is your Quarto document, in a note next to the code that came out of the request. Your report shows the code anyway (Chapter 2); with these notes, readers can also trace how it came about. In any case, you are responsible for the code, the results and their interpretation.

Note

Research journal: Where your mini study stands. Your mini study is complete and reproducible. If you extend it with the help of an assistant, record the requests in your research journal: which question you asked, what the answer suggested and what you checked and used.

Exercises

NoteExercise 1 · Request with context · Reproduction

You want to know how school leaving certificates (educ) are distributed in the West and in the East, weighted with wghtpew. Codes 6 (“OTHER SCHOOL CERTIF.”) and 7 (“STILL AT SCHOOL”) should count as missing. Fill in the template from Section 10.4 for this question. Include the variables with names, labels and values, but no data.

TipSolution 
I am working in R (version: 4.6.2) with the tidyverse and the mariposa package (version: 0.7.4).
Documentation for mariposa: https://yannickdiehl.github.io/mariposa/llms.txt

[rules as in the template]

My variables (name, label, values):
- educ: RESP: GENERAL SCHOOL LEAVING CERTIFICATE; 1 = NO CERTIFICATE,
  2 = LOWEST LEVEL, 3 = INTERMEDIARY LEVEL, 4 = QUALI.UNIV.APPL.SCI.,
  5 = QUALI.FOR UNIVERSITY, 6 = OTHER SCHOOL CERTIF., 7 = STILL AT SCHOOL
- eastwest: REGION OF INTERVIEW: WEST - EAST; 1 = OLD FEDERAL STATES,
  2 = NEW FEDERAL STATES
- wghtpew: WEIGHT: EAST-WEST, PERSON-LEVEL

What I want to do:
A weighted frequency table of educ, separately for West and East.
Codes 6 and 7 should count as missing.

My code so far:
allbus <- read_spss("ALLBUS2023.sav") |>
  set_na(-56, -55, -54, -53, -51, -50, -42, -41,
         -33, -32, -15, -11, -10, -9, -8, -7, -6)

A suitable answer uses, for example, set_na(educ = c(6, 7)) from Section 4.8, then group_by(eastwest) and frequency(educ, weights = wghtpew). Check it with the steps from Section 10.5 before you use it.

NoteExercise 2 · Checking an answer · Reproduction

An assistant suggested this code for the question “How satisfied are people in the West and in the East with their lives, and how satisfied are they in Germany as a whole?” Find at least three problems, first by reading. Then check your guesses in R.

allbus %>%
  mutate(east = eastwest == "East") %>%
  group_by(east) %>%
  summarise(mean = mean(ls01))

mariposa::weighted_mean(allbus$ls01, allbus$wghtpew)
TipSolution
  • %>% works, but it does not match the style of this book (|>).
  • eastwest is a number with labels (1 and 2). Comparing it with the text "East" causes an error.
  • mean() without na.rm = TRUE returns NA as soon as ls01 has missing values (Section 3.6).
  • The means for West and East are unweighted.
  • mariposa::weighted_mean() does not exist. In mariposa the function is called w_mean(), and it expects a dataset and variable names instead of allbus$….

In the style of this book:

allbus |>
  group_by(eastwest) |>
  describe(ls01, weights = wghtpew)

allbus |>
  w_mean(ls01, weights = wghtpew)
NoteExercise 3 · Checking functions · Transfer

An assistant suggests four mariposa functions for your analysis: cross_table(), w_sd(), crosstab() and cronbach_alpha(). Check which of them exist. For the others, find the matching function from this book.

TipSolution 
c("cross_table", "w_sd", "crosstab", "cronbach_alpha") %in% ls("package:mariposa")
[1] FALSE  TRUE  TRUE FALSE

w_sd() and crosstab() exist. Instead of cross_table() you use crosstab() from Chapter 7, and instead of cronbach_alpha() the function reliability() from Section 8.7.

NoteExercise 4 · A step for your mini study · Mini research question

Take your own research question from the exercises of the previous chapters and think of a next analysis step that you have not learned yet, for example an additional control variable or a different graph. Write a request for it with the template and check the answer with the steps from Section 10.5. Record in your Quarto document what you asked, what you changed in the answer and why.

There is no model solution for this exercise. What matters is the process from the request to the check.

What you know now

  • A language model writes the code that is most likely given its training texts. For mariposa, it therefore easily invents functions and arguments.
  • You give an assistant context: goal, versions, the mariposa documentation, variables and error messages.
  • You reproduce problems with data using made-up example values.
  • You check suggestions with the R help, with ls("package:mariposa") and with simple checks of the number of cases, the range of values and the weights.
  • You take numbers only from your own R output.
  • You do not give ALLBUS data to any AI system, because the GESIS terms of use prohibit it.
  • In coursework and theses, you state what you used an assistant for.
